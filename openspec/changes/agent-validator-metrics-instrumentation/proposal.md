## Why

Agent Validator already extracts useful model-usage evidence from several review adapters, but it reduces that evidence to provider-specific console strings and debug-log entries. The adapter contract returns only review text, and the structured run result contains gate outcomes but no model identity or usage data. The documented log prefixes have already drifted behind the adapters that emit them, illustrating why console strings are not a stable contract. Downstream callers therefore cannot reliably determine which model was requested or used, distinguish known zero usage from unavailable telemetry, associate usage with a particular review attempt or Validator invocation, or aggregate retries without scraping human-oriented logs.

This is already limiting real evaluation workflows: captured validator output contains telemetry lines alongside review results, but those lines are not a stable data contract and omit explicit provenance and completeness. Agent Validator should publish the information it owns as versioned, machine-readable evidence while leaving downstream systems free to apply their own pricing and evaluation policies.

The cross-product boundary is intentional: Validator owns measurement, Runner owns workflow attribution and consolidation, and Evals owns evaluation and pricing. Runner-driven evaluations consume Runner's consolidated artifact rather than independently counting Validator snapshots as a second usage source. Validator remains independently usable through its standalone artifact, including by callers that do not use Runner.

**Verdict: go with caveats.** The change fits Agent Validator's responsibility because its adapter layer is the authoritative boundary for model dispatch and provider telemetry. The contract must remain honest about uneven adapter support: requested identity is not proof of effective identity, missing categories are not zero, and aggregates are complete only to the extent established by their underlying attempts.

## What Changes

- Add a full, versioned validation-metrics artifact at `<log_dir>/validation-metrics.json`, giving CLI callers a stable discovery contract without parsing console or `--report` output. The dedicated artifact remains usable after review logs are cleaned and avoids requiring consumers to scan or reconstruct a contract from mutable per-review JSON files.
- Create a stable `invocation_id` for every `run`, `review`, and `check` command execution, including executions that dispatch no model because they exit early with outcomes such as no changes, trusted, no applicable gates, lock conflict, or error. Each invocation records its session association when established, status, timestamps, completeness, child attempt IDs, and usage aggregates. The fixed artifact exposes both the current invocation and cumulative validation-session aggregates so a caller never has to diff successive session snapshots to identify its own usage. A lock-rejected command returns its own identity and explicit zero-dispatch outcome without mutating the active command's shared snapshot. When configuration, lock ownership, or storage prevents publication or session association, the result explicitly reports that limitation rather than identifying an earlier snapshot as the current command's metrics.
- Record one durable attempt for every actual model-backed review dispatch and parent it to the invocation that caused it. Each attempt includes a stable deduplication ID, validation-session identity, invocation identity, gate and review-slot context, retry/run number, adapter, timing, outcome, requested identity, zero or more effective identities when established, usage provenance, adapter-observed usage fields, normalized token categories, fidelity, and explicit completeness or unavailability reasons. When a dispatch reports multiple effective models, preserve per-model usage only where the provider reports it; otherwise retain usable attempt-level unallocated usage and report `per_model_attribution` as `complete`, `partial`, or `unavailable` rather than manufacturing an allocation.
- Persist attempt identity and initial state before dispatch, then finalize the same attempt after success or failure. Interrupted attempts remain explicitly incomplete, while parallel reviews and later validator retries add distinct attempts to the same validation-session history. Persistence failures warn and mark publication or history degraded without preventing validation or changing its outcome or exit code; failed persistence is never presented as durable evidence.
- Treat skipped reviews and preserved one-shot results as non-dispatches rather than zero-usage model attempts; their enclosing command still has an invocation record. Correlate actual review results and review JSON artifacts with their telemetry attempt IDs.
- Normalize usage into the semantic fields `input_total`, `input_uncached`, `cache_read`, `cache_write`, `output`, `reasoning`, and `provider_total`. Every value identifies whether it is directly observed or derived and whether it is included in another field. A normalized grand total is unavailable unless the contributing categories are demonstrably non-overlapping.
- Derive invocation and session aggregates from the attempt records, including attempt counts, semantic token-category subtotals, identity groupings, coverage, and completeness. Each aggregate measurement carries a typed availability envelope with known subtotal, applicable coverage, fidelity, and reasons for unavailable or incomplete values. Unknown or unavailable values never silently contribute zero, and partial aggregates remain labeled as partial. Attempts are the accounting authority; summaries are deterministic derived views, not additional consumption. Summed attempt durations are not represented as elapsed time when intervals overlap.
- Define a validation session as the initial validator run plus its retries while they share the current log set. A clean ends that session. Persist the session identity across processes so failed runs and later retries append to the same history, and start a new identity for the next session.
- Keep `<log_dir>/validation-metrics.json` as a persistent latest-session snapshot that does not trigger rerun detection, current-log detection, or clean rotation by itself. Session closure finalizes the session, writes an immutable historical copy when retention is nonzero, atomically replaces the fixed latest snapshot, and persists the closed boundary so the next invocation starts a new session even when no ordinary logs existed. Historical metrics follow `max_previous_logs`; a depth of zero retains the fixed latest snapshot without historical telemetry archives. Pending Runner delivery evidence is separate from historical retention and survives ordinary cleanup at every depth until Runner acknowledges durable receipt or the user explicitly discards it.
- Expose `session_id`, `invocation_id`, and the fixed artifact path through documentation and the programmatic run result while preserving existing console and `--report` behavior.
- Document telemetry support as a field-level matrix with collection prerequisites. Unavailability reasons distinguish an adapter that cannot report a field from telemetry that was disabled or redirected by the caller's environment. Requested and effective identity remain separate, with provenance describing how each effective value was established.
- Preserve adapter-observed usage evidence separately from normalized token fields, distinguish observed from derived values, and retain exact or approximate precision independently of derivation. Durable raw evidence is restricted to an allowlisted identity-and-usage structure with provider-native values and source metadata when available; prompts, responses, environment values, credentials, and unrestricted provider event payloads are never included. Reconstructed summaries such as rounded CLI display values are never presented as exact raw evidence.
- Require each adapter parser to be validated against recorded representative CLI output, including combinations of metric and request events, before its values can be labeled complete. Agent Validator does not apply pricing tables or convert usage into an estimated cost policy.
- Define a common versioned model-attempt measurement contract for Validator telemetry and Runner's own model telemetry. Distinct outer artifact schemas share measurement semantics rather than maintaining lossy translations. Preserve requested configuration, resolved launch configuration, and telemetry-observed effective identity separately; a resolved model is not evidence of the observed effective model. Derived values retain the precision of their inputs instead of conflating derivation with exactness.
- Require producer version/build provenance and adapter/parser-mapping version, plus underlying CLI and usage-source format/event versions or explicit unavailability. Preserve these details through the handoff so historical measurements remain interpretable.
- Provide a versioned Validator-owned CLI for consumer-scoped telemetry export and acknowledgment, using the same recorded evidence as the standalone snapshot. Runner supplies originating workflow/run/step-attempt correlation context when launching validation, then retrieves evidence through the CLI after execution, including failure, and during recovery. Validator resolves its own storage from the project/configuration context; Runner does not read snapshot or outbox files directly. Export preserves all accounting and attribution semantics, including partial identity, multiple models, unallocated usage, provider-reported cost, attempt lifecycle evidence, and invocation finalization with legitimate zero-dispatch outcomes. Metrics commands never run validation. This pull protocol replaces the previously proposed JSONL sink; supporting both transports is not included in this change.
- Support recoverable delivery and idempotent ingestion of retained evidence: updates and replay preserve the original attempt, command invocation, validation session, and originating workflow attribution. Recovery delivery is not newly incurred model work. Exports return an opaque receipt identifying the exact exported record revisions; Runner durably incorporates those measurements before calling Validator's acknowledgment CLI. Acknowledging an older revision cannot release a newer update, and repeated acknowledgment is harmless. Export alone does not consume pending evidence or establish receipt. Pending handoff evidence survives ordinary cleanup, rotation, and zero historical retention until acknowledged or explicitly discarded by the user. Pending data may accumulate while delivery is broken; cleanup must not silently evict it. An explicit discard is not successful delivery and must leave the delivery gap visible. No matching invocation is missing evidence, not confirmed zero consumption. Storage failures remain subject to the warning-and-degraded-history policy rather than an unconditional durability guarantee; standalone snapshot publication and consumer delivery states remain independent.

## Capabilities

### New Capabilities
- `validation-metrics`: Common versioned measurement semantics; session, invocation, and attempt identity; requested, resolved, and observed effective identities; adapter-observed and normalized usage; accounting relationships; per-model attribution; version provenance; fidelity; explicit completeness; review-result correlation; typed derived invocation/session aggregates; and fixed-path artifact discovery.
- `nested-metrics-handoff`: Consumer-scoped versioned CLI export and receipt acknowledgment; attempt lifecycle and invocation-finalization records; zero-dispatch evidence; independent snapshot/delivery states; protected pending evidence; recoverable replay with stable original attribution; and contract fixtures for downstream interoperability.

### Modified Capabilities
- `run-lifecycle`: Define, initialize, resume, and finalize validation-metrics sessions and command invocations; retain attempts across failures and reruns; represent zero-dispatch and interrupted invocations honestly; and expose session/invocation identity and the metrics artifact through structured run results.
- `log-management`: Close sessions with a crash-safe finalize/archive/latest-snapshot transition, keep the latest validation-metrics snapshot persistent and non-triggering, rotate historical metrics according to `max_previous_logs`, and preserve pending delivery evidence independently of historical retention, including at depth zero.

## Technical Approach

Introduce a telemetry domain model at the adapter boundary instead of reparsing the adapters' existing display strings later in the run. Adapters return review output together with structured telemetry evidence, or attach the same structured evidence to a typed failure. Each adapter maps what its CLI actually reports into separate observed and normalized representations: allowlisted provider-native identity/usage values where available, explicitly derived or approximate values where that is all the CLI exposes, and a conservative normalized token view for cross-adapter aggregation. Arbitrary provider payloads, prompts, responses, environment values, and credentials do not enter the metrics artifact. Unsupported identity or token fields carry an explicit unavailable or partial state and reason, including whether caller-controlled environment settings redirected collection.

A lifecycle-scoped metrics recorder sits above run orchestration and adapter execution. It allocates a stable invocation ID for every validation command execution and a stable attempt ID for each model dispatch beneath it. It persists an attempt before invoking the CLI when storage permits, finalizes that record on every controlled success or error path, and safely coordinates parallel review updates. Write failures warn and leave publication/history explicitly degraded rather than changing validation behavior. It also finalizes invocation records on zero-dispatch and early-return paths; results distinguish successful publication from unavailable or stale snapshots. Lock-rejected invocations do not modify the lock owner's shared snapshot. The validation-session identity persists across the initial run and retries that share a current log set, with clean marking the boundary before the next session. Review gate results retain the attempt ID so consumers can join findings, failures, and usage without relying on filenames or execution order. Existing provider telemetry log lines may remain for humans and compatibility, but they are no longer the data source for the machine-readable contract.

The recorder materializes the standalone, schema-versioned `<log_dir>/validation-metrics.json` artifact containing attempt history and derived aggregates. Keeping the complete consumer contract in one persistent snapshot is intentional: per-review JSON remains mutable review evidence, may be archived or deleted during clean, and would otherwise force consumers to scan and join multiple files. Review JSON receives only the attempt reference needed for correlation.

The Runner handoff is another projection of that same evidence, not a second accounting implementation. It uses a versioned model-attempt measurement payload with lifecycle and command-finalization context. Runner supplies correlation context at launch, exports measurements through Validator's CLI in that same project/configuration context, durably consolidates them, and acknowledges the opaque export receipt through Validator's CLI. Runner need not discover or interpret private storage paths. The receipt binds exactly the exported revisions, so acknowledging an in-progress record cannot remove a later completion update. Export and acknowledgment do not launch validation or create model consumption; replay after a crash is safe for a deduplicating consumer. Missing invocation evidence remains distinguishable from a finalized empty attempt set and from previously acknowledged delivery.

Runner adds workflow, execution-session, and parent-step attribution without replacing producer identifiers, manufacturing effective identities, or dropping accounting metadata. Producer validation-session IDs, command invocation IDs, model attempt IDs, Runner execution-session/parent-step IDs, and provider CLI session IDs remain distinct. Transport revisions and replay update one measured attempt rather than adding usage; actual new dispatches create new attempts. Unknown history remains explicit when evidence is insufficient for recovery. Exact CLI spelling, launch-context representation, wire layout, schema ownership/distribution, receipt persistence, and replay scheduling are design decisions to coordinate with companion consumers before implementation. A private protected outbox is a candidate storage mechanism, not a consumer-facing file contract. The earlier `AGENT_RUNNER_NESTED_METRICS_PATH` JSONL transport is superseded for this integration, not retained as a second delivery route.

Normalization uses the explicit semantic fields `input_total`, `input_uncached`, `cache_read`, `cache_write`, `output`, `reasoning`, and `provider_total`. Each value carries source, fidelity, derivation, and inclusion metadata so consumers can distinguish a subtotal from an overlapping category. Aggregate grand totals are produced only from categories proven non-overlapping; otherwise the total and its reason remain unavailable. Multiple effective models may share unallocated attempt-level usage, with per-model attribution completeness reported independently from overall usage completeness.

Aggregation sums only reported values, preserves provider category semantics, reports fidelity and coverage for each identity and usage dimension, and marks totals partial whenever relevant attempts or categories are unavailable. The artifact provides separate current-invocation and cumulative-session views. Reruns append new invocations and attempts to the active validation session; they do not overwrite failed attempts or reuse an attempt ID for a new dispatch. The latest snapshot is excluded from predicates that detect reruns or decide whether clean should rotate logs.

Session closure is a crash-safe ordered transition: finalize the current session, write an immutable metrics copy into that session's archive when retention is nonzero, atomically replace the fixed latest snapshot, then persist the closed-session boundary used to allocate the next session ID. This transition runs even when no ordinary logs need rotation. Historical session copies remain subject to configured rotation; depth zero retains the fixed latest snapshot without historical archives. Independently, pending handoff evidence remains protected until acknowledged durable receipt or explicit user discard. That evidence does not itself reopen a closed validation session or trigger rerun/current-log detection. Receipt persistence and explicit-discard mechanics remain design work; neither ordinary cleanup nor successful export establishes receipt. Protection covers Validator-managed cleanup, not external directory deletion or disk loss.

This approach keeps pricing downstream. Provider-reported cost, when present in observed telemetry, remains evidence rather than an Agent Validator estimate; no pricing normalization, rate lookup, or estimated-cost completeness claim is introduced here. Evals applies versioned pricing policy separately and can reprice without rewriting measurement evidence. A domain-specific JSON contract is preferred over requiring OTLP-JSON because adapter support is uneven and the contracts must express attempt identity, review correlation, retries, fidelity, and completeness. The measurement vocabulary is shared across products while outer validation and workflow artifacts remain domain-specific. Versioned schemas, representative fixtures, and compatibility tests come before introducing a shared runtime library or service. Attempt-only standalone artifacts are insufficient because unknown-aware derived aggregates remain an explicit consumer requirement.

## Cross-Repository Coordination and Acceptance

Agree on the common measurement and handoff contracts before implementing the producer. Prepare Runner and Evals review handoffs in this change directory, resolve consequential consumer feedback, then implement and accept integrations in the order Validator, Runner, Evals. Implementation may overlap after contracts and representative fixtures are agreed. Companion work adapts Runner's own measurements and nested ingestion/consolidation, then Evals ingestion and valuation; it is not implemented by this Validator change.

Validator acceptance establishes that the producer meets its contract, not that end-to-end evaluation metrics are complete. Cross-product acceptance must additionally demonstrate parallel reviews, actual retries, interrupted and recovered attempts with original attribution, zero dispatch, requested-only identity, multiple models with unallocated usage, publication failures, pricing independence, and no duplicated consumption or elapsed duration.

## Out of Scope

- Implementation changes in Agent Runner or Agent Evals, including their result schemas and ingestion/pricing logic. Those belong to coordinated companion changes; contract planning and handoff documents for them are included here.
- Modification or regeneration of the stopped evaluation artifact used as read-only evidence for this proposal.
- Pricing tables, estimated-cost policy, currency conversion, billing reconciliation, or eval scoring.
- Historical backfill by scraping existing console, debug, or review logs.
- Durable storage of prompts, responses, environment values, credentials, unrestricted provider events, or other raw payload fields outside the allowlisted identity-and-usage evidence structure.
- Inferring that a requested model, provider, or effort was effective when the adapter cannot verify it.
- Treating unavailable telemetry fields as zero or claiming a complete aggregate from partial attempt history.
- Promising effective-model extraction for an adapter until representative CLI evidence demonstrates that the field is available and trustworthy.
- Attribution of separate provider-internal API requests as independent review attempts; one validator adapter dispatch is one attempt, while provider request counts remain usage evidence when reported.
- A general-purpose telemetry server, exporter protocol, or remote observability backend.

## Impact

- **Adapter contract and implementations:** `src/cli-adapters/` will return structured execution and telemetry results while retaining review text and current human-readable logging. Adapter-specific parsers will expose actual identity and token support without manufacturing unsupported fields, tag fidelity, explain environment-conditioned gaps, and gain representative recorded-output fixtures.
- **Review execution and results:** `src/gates/` will allocate/correlate attempt IDs, persist controlled failures, and add attempt references to per-review results and JSON artifacts, including multiple gates, slots, parallel dispatches, one-shot behavior, and retries.
- **Run orchestration and public types:** `src/core/` will manage validation-session and invocation lifecycles and derive their separate aggregates; `src/types/validator-status.ts` will expose additive `session_id`, `invocation_id`, and metrics artifact metadata through `RunResult`.
- **Persistence and cleanup:** log-management code will write the versioned latest snapshot safely, exclude it from rerun and empty-clean triggers, and perform the explicit session-close archive transition according to configured depth without losing failed or resumed attempts from the active session.
- **Documentation and tests:** adapter support documentation, schema documentation, contract tests, zero-dispatch and early-exit invocation tests, failure/resume tests, token-overlap and aggregation tests, multi-model attribution tests, session-close interruption tests, parallel multi-review tests, raw-evidence safety tests, and compatibility tests will be added or updated.
- **Runner handoff:** the producer exposes consumer-scoped CLI export and receipt acknowledgment for lifecycle and invocation-finalization evidence, preserves measurement/version semantics and original caller context, protects unacknowledged revisions, and exposes delivery limitations. Companion review briefs and shared contract-fixture obligations cover Runner consolidation and Evals ingestion without modifying either sibling repository in this change.
- **Compatibility:** Existing CLI output, review findings, exit codes, and `--report` text remain compatible. Review JSON and programmatic result additions are additive. No new runtime dependency is expected.
