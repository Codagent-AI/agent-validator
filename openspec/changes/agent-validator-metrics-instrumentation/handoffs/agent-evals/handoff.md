# Handoff: Agent Evals measurement ingestion and valuation integration

## Objective

Consume trustworthy workflow measurements through Agent Runner, including Validator review attempts, and apply evaluation/pricing policy without losing uncertainty, reconstructing metrics from logs, or double-counting attempts.

## Current State

The user approved this cross-product architecture: Validator owns measurement, Runner owns workflow attribution/consolidation, Evals owns evaluation/pricing. The proposal, all four specifications, and `design.md` are written. The design now defines concrete measurement envelopes, CLI/record contracts, independent versions, and receipt/recovery semantics. Executable JSON Schemas, shared fixture files, and the producer/integrations are not implemented yet. The approved handoff uses Validator CLI export and receipt acknowledgment, replacing the earlier JSONL-sink proposal.

The user approved companion contract reviews now, resolving consequential feedback with the user before editing the approved contract, and accepting integrations in the order Validator → Runner → Evals. Implementation can overlap after contracts and fixtures are agreed. This review is read-only: do not modify files in any repository. Evals code changes belong to a separately authorized companion change. Do not modify the stopped evaluation artifact or regenerate its metrics.

Inspection during integration review confirmed that Evals reads only Runner's `run-metrics.json` for implementation metrics and now accepts schema v1/v2/v3. Do not plan already-completed v3 enablement again. The reviewed consumer still hardcodes normalized `usage_source_version` to null, substitutes zero for omitted cache categories when deriving billing tokens, and assumes a single model per normalized attempt. Its reported-cost fast path treats an available amount as resolving an attempt. These observations identify companion integration work, not constraints on the desired architecture; recheck current code before editing.

## Key Decisions

- **Single ingestion authority:** For Runner-driven evaluations, consume Runner's artifact. Do not add direct Validator snapshot ingestion as a fallback or second accounting source. A future standalone Validator evaluation could use Validator's standalone artifact as its own authoritative route.
- **Runner retrieves through Validator's CLI:** Runner supplies original correlation context at launch, exports through a versioned Validator CLI, durably stores the evidence, then calls Validator to acknowledge the opaque receipt for the exact exported revisions. Private storage paths are not part of this contract. Export is non-consuming; acknowledgment of an older revision does not release a newer completion. Evals does not implement this handoff itself or acknowledge on Runner's behalf.
- **Bounded delivery:** Runner drains bounded receipt-scoped batches through save/ack/re-export. A terminal invocation can arrive separately from its attempts, so delivery completeness requires reconciled membership, imported heads, batch coverage, and gaps. No `context_records` field exists in v1; original parent IDs and retained incorporated records provide context. `metrics pending` provides bounded operator discovery, not an Evals fallback or proof of zero usage. Overlapping old receipts no longer pin payloads after those revisions have durable dispositions; small idempotence/gap metadata remains.
- **Lossless measurement contract:** Runner-native and Validator attempts share versioned measurement semantics within their distinct domain artifacts. Evals must preserve the semantics, not flatten unknown fields into numbers or discard usable aggregate evidence.
- **Identity:** Requested, resolved launch, and telemetry-observed effective identity are distinct. Missing effective identity can prevent pricing without invalidating measured tokens. Preserve producer identifiers and original workflow attribution across retries and recovery.
- **Token accounting:** Canonical fields are `input_total`, `input_uncached`, `cache_read`, `cache_write`, `output`, `reasoning`, and `provider_total`, with availability, provenance, inclusion relationships, precision, and derivation. Total-token completeness does not imply complete billing categories. Omitted/unsupported categories are not observed zero.
- **Multiple models:** Preserve actual per-model allocations, unallocated attempt usage, and independent attribution completeness. Multiple identities do not justify splitting counts equally, duplicating an aggregate across models, or counting one dispatch as several attempts.
- **Stable joins:** Allocations have stable attempt-local `allocation_id` values and available/unavailable references to observed `identity_id` entries. `provider_reported_costs[]` uses stable `cost_evidence_id` values and explicit attempt/allocation/unavailable scope, allocation references, amount/currency availability, coverage, precision, and overlap. References resolve within one complete attempt revision; revised values do not imply a new dispatch or a new allocation identity.
- **Provenance:** Retain producer version/build details, parser/mapping version, underlying CLI version or explicit unavailability, and source format/event version or explicit unavailability. Preserve allowlisted provider-native evidence separately from normalized values.
- **Attempts and delivery:** Replayed measurements and successive lifecycle revisions describe the same original work. Actual new dispatches have new attempt IDs. A finalized zero-dispatch invocation is not a model attempt with fabricated provider observations. Incomplete collection and incomplete delivery remain explicit.
- **Pending delivery retention:** The user approved preserving pending Validator telemetry through ordinary cleanup and zero historical retention until Runner acknowledges durable receipt or the user explicitly discards it. Successful export is not acknowledgment; explicit discard is a delivery gap, not zero consumption or successful receipt. Recovery can deliver old measurements later without making them newly incurred work.
- **Aggregates:** Attempts are the authority; aggregate envelopes expose state, known subtotal, fidelity, and coverage per measurement. Never add summaries to attempts or allocation rows to their parent totals. Preserve history, usage, attribution, pricing, and delivery completeness independently.
- **Valuation:** Keep provider-reported cost distinct from Evals-calculated estimates. Record pricing source/version or retrieval date, currency, rates, and approved assumptions. Repricing changes valuation, not the underlying evidence. Unpriceable work yields a known subtotal and incomplete total, not a zero-cost attempt.
- **Timing:** Preserve attempt work duration separately from workflow elapsed/active duration. Parallel and nested work overlaps and must not be added again to elapsed time.
- **Safety:** No prompts, responses, credentials, environment values, unrestricted provider payloads, or account/user/organization/email/host identifiers in telemetry fields, source metadata, or diagnostics. Permitted opaque execution/session IDs remain distinct from principal identity and must not encode excluded identifiers. The stopped eval artifact remains read-only evidence.
- **Concrete versions and ownership:** Common measurement, Validator standalone artifact, CLI protocol, and capabilities each begin at independent version 1. Validator initially owns language-neutral schemas/fixtures; consumers pin reviewed versions without sharing a runtime. Runner independently versions its workflow artifact. Unsupported meanings must not be silently downgraded.
- **Mixed measurement versions:** Each immutable invocation/attempt revision carries its own `measurement_schema_version` inside its digest input; retained sessions/scopes can span upgrades. Root version sets describe contents, not a conversion. Validator separately declares root `aggregate_measurement_schema_version`; Runner/Evals must preserve source versions and make their own aggregate interpretation explicit. Select the actual latest head, never an older compatible revision. Combine across versions only through reviewed semantic mappings with provenance; otherwise keep known compatible subtotals with explicit coverage limitations or separate semantic groups. Export negotiation is Runner's responsibility, not Evals' reason to scrape Validator directly.
- **Closed schema evolution:** Fields and source variants are frozen within each published schema version; additions, even optional fields, require a new owning-contract version. Preserve all supported data, including declared optional fields. Reject unsupported fields/versions rather than forwarding opaque unknown data or dropping it silently. Runner must not acknowledge an unsupported record. This replaces the prior unknown-field-forwarding policy.
- **Producer integrity:** Validator and Runner verify SHA-256 over RFC 8785 JCS serialization of the complete producer record excluding top-level `digest`; preserve that digest/revision alongside the accepted evidence. Evals need not rehash merely to price. Export/acknowledgment remain usable while Validator closure is unfinished, without a new validation or clean command.
- **Concrete measurement envelopes:** Token fields carry `state`, value/known subtotal, observed/derived origin, exact/approximate precision, source references, derivation, relationships, and reasons. Aggregate fields carry state, `known_subtotal`, precision, explicit eligible/contributing/partial/missing attempt coverage, and reasons. `normalized_total` is distinct from `provider_total`. See `design.md` for the complete designed shape; no source completeness or priceability follows merely from a numeric total.
- **Revision and gap semantics:** Invocation/model-attempt records use producer IDs and increasing integer revisions with replacement payloads. Prepared-only attempts retain uncertainty. Exports distinguish pending, previously acknowledged, discarded, and missing evidence. Receipt-scoped discard leaves a durable gap that acknowledgment cannot erase. Runner must carry these distinctions forward, not present them as zero-cost work.

## Approved Companion Obligations

- **Multi-model reporting:** Keep each dispatch as one authoritative attempt. Show source-supported attributed allocation rows and an explicit unallocated row with observed identity context. Separate overall dispatch count from per-row participating-attempt counts; those counts are not additive across rows. Token totals may be complete while model attribution is incomplete.
- **Scoped valuation:** Available cost alone does not resolve the whole attempt. Require established full coverage of that attempt, or exhaustive non-overlapping coverage across its allocations/work. Allocation costs contribute only to their covered scope; partial/unallocated remainder leaves a known subtotal and incomplete total. Do not sum overlapping whole-attempt and allocation costs. Preserve unknown/non-USD currency as measurement evidence; USD reporting and any conversion are downstream policy, not a producer restriction.
- **Replacement revisions:** Consume Runner's new outer-artifact version with one selected head per producer attempt, retaining revision, digest, original attribution, and gaps. Do not duplicate work because both prepared and terminal records were delivered, and do not confuse a real retry with replay.
- **Billing categories:** Preserve envelopes. For `input_total=100`, `cache_read=40`, and unavailable `cache_write`, do not assume 60 uncached tokens. A known normalized total alone is not priceability; only derive billing categories from established availability/inclusion relationships.
- **Migration scope:** Evals v3 support already exists. The required work is support for the new Runner measurement representation/version, multi-model/partial evidence, scoped costs, and strict versioned allowlists—not v3 enablement again.
- **Cross-version and batch coverage:** Test a mixed-version session/scope carried losslessly in Runner's new artifact, with comparable and incompatible aggregate inputs and no fallback to older heads. A partially imported batch set must remain incomplete even if it contains terminal invocation evidence. Preserve privacy exclusions and source versions through valuation/reporting; lack of delivery or interpretation is not zero usage or cost.
